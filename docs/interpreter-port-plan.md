# Plan: porting the Rust interpreter to Boring

**Date:** 2026-06-10  
**Status:** Draft — preliminary analysis, no code written yet  
**Goal:** rewrite the interpreter (`src/interpreter/`) in Boring, transpile it to single-threaded Rust, and have it pass the existing test suite.

## 2. Feasibility analysis — challenges per component

### 2.1 `Value` (enum with 25+ variants)

```rust
pub enum Value {
    Nil, Void, Bool(bool), Int(i64), Uint(u64), Float(f64),
    Str(String), Array(Vec<Value>), Tuple(Vec<Value>),
    Dict(Vec<(Value, Value)>), Set(Vec<Value>),
    Object(Rc<RefCell<ObjectInner>>),
    EnumVariant { type_name, variant, fields },
    Fn { decl: FnDecl, captured: EnvRef },
    Closure { params, body, captured },
    NativeFn { name, func: fn(&[Value], usize) -> Result<Value, Signal> },
    OverloadedFn { name, variants },
    Channel { buf: Rc<RefCell<VecDeque<Value>>>, ... },
    ...
}
```

**Challenges:**
- `NativeFn` holds a **Rust function pointer**. In Boring, a function type `Value([Value])` in a field position is transpiled to `Rc<dyn Fn(Vec<Value>) -> Value>` — storable and cloneable. The `NativeFn` variant can therefore be ported directly without structural changes.
- The `Fn` and `Closure` variants hold `captured: EnvRef` which is `Rc<RefCell<Env>>`. In single-threaded Boring, `Rc<RefCell<T>>` is generated by the transpiler via `T'actor` — no issue.
- `Channel` with a shared `Rc<RefCell<VecDeque<Value>>>` between sender and receiver — same remark.

### 2.2 `Env` (chained scopes)

```rust
pub struct Env {
    vars: HashMap<String, Value>,
    mutable: HashSet<String>,
    shared_mutable: HashSet<String>,
    parent: Option<EnvRef>,     // EnvRef = Rc<RefCell<Env>>
}
pub type EnvRef = Rc<RefCell<Env>>;
```

`Env` is a tree of scopes shared via `Rc<RefCell>`. Closures capture their parent `EnvRef`. This is the heart of the execution model.

**In Boring:** the structure ports directly. `HashMap` is available in the stdlib. The recursive `Env → parent: Option<EnvRef>` is expressed as `parent: Env'actor?`, which transpiles to `Option<Rc<RefCell<Env>>>` — pointer-sized, no indirection issue.

### 2.3 Mutual recursion between `exec` / `eval_expr` / `call`

All three modules call each other through `self` (the `Interpreter` struct). A flat port into a single `Interpreter` struct in Boring is the natural translation. No issue anticipated.

### 2.4 Native stdlib (~720 lines in `register_stdlib`)

The Rust interpreter registers ~30 native functions (`print`, `write`, `len`, `int`, `float`, `string`, math functions, etc.) as `NativeFn` values. In Boring, these will be implemented either as branches of a `NativeKind` enum or as ordinary Boring functions called from a central dispatcher.

**Estimate:** ~400 lines of Boring to cover all native functions.

### 2.5 Built-in methods (`methods.rs`, 2 098 lines)

All methods on `Array`, `Dict`, `Set`, `String`, `Range`, `Channel`, etc. — dispatched via `call_method`. These are pure data-manipulation functions with no function pointers, making them a straightforward 1-to-1 port.

## 4. Architecture options

### Option A: standalone Boring interpreter (recommended for this port)

The `.boring` file reads source via stdin or file path, receives the AST from the Rust front-end via serialization, and executes it.

**Problem:** the AST is defined in Rust. The Boring interpreter needs access to the same representation.

Two sub-options:
1. **Duplicate the AST in Boring** — rewrite the AST structs/enums in Boring (~500 lines, direct port of `src/ast/mod.rs`). The Rust parser serializes to JSON; the Boring interpreter deserializes it. Simpler to implement first.
2. **Port everything** — also port the lexer, parser, and checker to Boring. Scope ×3, but more coherent long-term.

For this initial port, **Option A with serialized AST** is the most realistic. The pipeline becomes:
```
source.br → Rust parser → AST JSON → Boring interpreter → output
```

### Option B: replace only the interpreter module

Keep the entire Rust front-end (lexer, parser, checker) and replace only the execution phase. The Boring interpreter is called from `main.rs` via a Rust stub that passes a serialized `Program`.

This is essentially Option A — the distinction is whether the entry point stays in Rust or moves to Boring.

## 5. Suggested development order

1. **`ast.boring`** — Port the AST types from `src/ast/mod.rs`. ~500 lines. Everything else depends on this.
2. **`value.boring`** — `Value`, `Signal`, `RuntimeError`, `IndexValue`. ~300 lines.
3. **`env.boring`** — `Env`, `EnvRef`. ~150 lines.
4. **`stdlib.boring`** — Native functions ported as ordinary Boring functions + `NativeKind` dispatcher. ~400 lines.
5. **`methods.boring`** — Built-in methods on collections and strings. ~800 lines.
6. **`eval_expr.boring`** — Expression evaluation. ~600 lines.
7. **`exec.boring`** — Statement execution. ~700 lines.
8. **`call.boring`** — Call dispatch. ~400 lines.
9. **`main.boring`** — Entry point: read AST JSON, run interpreter.

**Total estimate:** 3 500–4 500 lines of Boring.

## 6. Open questions to resolve before starting

1. **AST serialization format:** JSON is the simplest choice. It requires a serializer on the Rust side and a deserializer on the Boring side — roughly ~300 extra lines on each side.
2. **Alternative without serialization:** is it possible to call the Boring interpreter directly from Rust by passing the Rust AST? This would require a shared representation — more complex.
3. **Tests:** the existing tests in `src/interpreter/tests.rs` (~5 600 lines) are Rust unit tests. The Boring interpreter will be validated against the 65 integration cases in `tests/cases/*.br`, which already have `.expected` output files.

## 8. Remaining language gaps

This section lists language-level gaps that still apply. Gaps that were already fixed as transpiler bugs have been removed.

### 8.1 `VecDeque<T>` (LOW impact)

`Value::Channel` uses `Rc<RefCell<VecDeque<Value>>>` for the internal buffer. `VecDeque` provides O(1) push-back / pop-front semantics, while `Vec` has O(n) pop-front.

**Current Boring support:** `Vec`-backed arrays only. No `VecDeque`.

**What is needed:** either `use std.collections.VecDeque` support in the interpreter, or a `VecDeque`-like stdlib entry in `stdlib/collections.br`.

**Workaround:** use a regular `[Value]` array with `remove(0)` for pop-front. Performance is O(n) but acceptable for the interpreter's simulation-only channels.

---


### 8.3 `any` as a usable field type (MEDIUM impact)

Several interpreter helper functions take or return `any`. In a Boring port, these would use `Value` directly — not `any`. The gap is more about ergonomics: `any` in Boring is `Named("any")`, which results in the Rust identifier `any`, which is not a valid type.

**Workaround:** use the concrete `Value` type everywhere in the Boring interpreter instead of `any`. This is the right approach and requires no language change.

### Summary table

| Gap | Impact | Has workaround | Language change needed |
|---|---|---|---|
| `VecDeque<T>` | Low | Yes (`[T]` + remove(0)) | Nice-to-have — add to `stdlib/collections.br` |
| `any` as a concrete type | Medium | Yes (use `Value` directly) | None — existing restriction is correct |
