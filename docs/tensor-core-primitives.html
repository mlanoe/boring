gpu.tensor.* — matrix/tensor-core acceleration primitives

Status: Proposed design. Not implemented — no parser, checker, or codegen changes have been made. This document is a research + feasibility study, produced the same way `warp-level-primitives.md` was before gpu.warp.* shipped: real vendor documentation, a concrete per-backend lowering table, a worked example, and an honest limitations section — but with no code behind it yet. Implementation is sequenced into discrete phases at the end of this document, each phase intended to become its own follow-up task.

Problem Statement

boring-llm (a real GPU-accelerated LLM inference engine written in Boring) was compared against llama.cpp for performance ceiling. Direct source inspection of boring's CUDA backend (src/transpiler/cuda/) confirms zero tensor-core support today — no wmma, no mma.sync, nothing, anywhere in the transpiler or docs/. The most sophisticated CUDA-specific primitive Boring currently exposes is warp-level shuffle (gpu.warp.shuffle_*, mapped straight to __shfl_*_sync — see warp-level primitives) plus block-level shared memory via bare 'actor. This is very likely the single biggest reason Boring-transpiled GEMM/attention kernels can't approach llama.cpp's real-world throughput on NVIDIA hardware — llama.cpp's CUDA backend (via cuBLAS or its own kernels) uses tensor cores for the bulk of its GEMM work on any reasonably modern NVIDIA GPU, and Boring has no equivalent path at all.

Real motivating pattern, checked directly: boring-llm/src/math_gpu.br's LinearKernel and Q8LinearKernel (16×16 shared-memory-tiled GEMM, fp32 accumulate; Q8LinearKernel additionally fuses Q8_0 dequantization into the tile-load step) are exactly the kind of kernel a tensor-core path exists to accelerate. The same file's LinearWarpKernel — a gpu.warp.*-based alternative added as a Phase 4 stretch item — is a useful, humbling precedent: its own doc comment reports it measured slower than the tiled kernel on real hardware (~1.5×–2.4× slower depending on shape), because removing barriers didn't address the actual bottleneck (data reuse via shared memory). That result is echoed explicitly in this document's own feasibility section below: a tensor-core rewrite must be benchmarked against linear_gpu/ q8_linear_gpu, not assumed to win, before it replaces anything.

gpu.warp.* is the direct design precedent for how Boring unifies a GPU-vendor-specific hardware primitive under one language-level surface. Its own README is instructive about the limits of unification, not just the form: gpu.warp.size is a single API but an backend/hardware-dependent value (32 on NVIDIA, 32-or-64 on AMD, a fixed constant 32 on wgpu's emulated fallback) — the primitive's shape is uniform, its concrete parameters are not. Tensor-core fragments turn out to need the same honesty, taken further: the tile shapes themselves don't unify across vendors at all (see "Known gaps" below) — this document proposes unifying the operation surface (declare a fragment, load it, multiply-accumulate it, store it) while being explicit that the legal (M, N, K, T) tuples are backend-specific and do not have a common intersection across CUDA and Metal today.

Vendor research summary

Full findings (with source URLs) are condensed here; see the per-backend lowering section for how each maps onto gpu.tensor.*.

CUDA — nvcuda::wmma (warp-level) and raw mma.sync/wgmma (PTX)

Source: CUDA C++ Programming Guide §7.24 "Warp Matrix Functions"; PTX ISA §9.7.16.5.14 "mma", §9.7.17 "wgmma".

  • API (<mma.h>, namespace nvcuda::wmma): `fragment<Use, M, N, K, T,

Layout>, fill_fragment, load_matrix_sync, mma_sync, store_matrix_sync. Use ∈ {matrix_a, matrix_b, accumulator}`.

  • Legal shapes are hard, compiler-enforced template constants — not a

runtime check: - fp16/int8/bf16 (__half/char/unsigned char/__nv_bfloat16) → fp32 or fp16/int32 accumulate: 16×16×16, 32×8×16, 8×32×16 (sm_70+ for fp16, sm_75+ for int8, sm_80+ for bf16) - tf32 (precision::tf32, explicit __float_to_tf32 conversion required): 16×16×8 only (sm_80+) - fp64: 8×8×4 only (sm_80+) - sub-byte int4/b1: experimental namespace, 8×8×32 / 8×8×128 (sm_75+, flagged for removal in future architectures except AND-mode b1)

  • fp8 (e4m3/e5m2, sm_89+/Ada) and everything Hopper's wgmma warpgroup-async

family covers (sm_90a+) are not exposed via the wmma C++ header at all — only reachable via raw mma.sync/wgmma.mma_async PTX (inline asm or a library like CUTLASS). This is a hard ceiling on mma.h, not an omission in the guide.

  • Warp-cooperative, opaque fragment layout: every load_matrix_sync/

mma_sync/store_matrix_sync call "must be called by all threads in the warp, or the result is undefined"; fragment element-to-lane mapping is "unspecified and subject to change in future architectures" — no portable manual indexing (the one exception: uniform elementwise ops via fragment::x[], e.g. scaling every element by a scalar).

  • Alignment: mptr must be 256-bit (32-byte) aligned; ldm must be a

multiple of 8 elements (__half) or 4 elements (float) — i.e. a multiple of 16 bytes either way. All template/call arguments must be identical across every thread in the warp.

  • Realistic GEMM loop: one accumulator fragment per output tile,

zero-filled once, then for each K-tile: load fresh matrix_a/matrix_b fragments, mma_sync(acc, a, b, acc) (true in-place C = A·B + C). Store once, after the loop.

What llama.cpp actually does — checked directly against ggml-cuda source

Since this whole proposal is motivated by a boring-llm vs. llama.cpp comparison, it's worth checking llama.cpp's own real usage rather than assuming wmma.h is "the" way developers use tensor cores in practice. It isn't, entirely:

  • wmma:: C++ is not llama.cpp's primary path today. Its FlashAttention

CUDA kernel originally used nvcuda::wmma, but PR #11583 replaced it with hand-rolled PTX mma.sync instructions (via the project's own thin mma.cuh wrapper) for every architecture except Volta — the author's stated reason: wmma::fragment's C++ abstraction imposes a fixed data layout that "allows for better optimization" once bypassed, i.e. the fixed fragment layout was a real ceiling on tuned performance, not just boilerplate. wmma:: C++ is kept only as the legacy path for the oldest tensor-core generation (V100/Volta, sm_70) — not deleted, but not where new optimization work happens either.

  • The single most structurally relevant kernel to this project is MMQ

(ggml/src/ggml-cuda/mmq.cuh) — fused dequantize + int8 matrix multiply, int32 accumulate, the same shape as boring-llm's own Q8LinearKernel (raw quantized bytes in, no separate dequant-to-float pass). MMQ picks its compute path by architecture: Turing+ (NVIDIA) or CDNA/RDNA3+-with-MFMA/WMMA (AMD) → an MMA/MFMA tensor-core int8 path; Pascal or older/no tensor cores → dp4a, a plain 4-wide int8 dot-product ALU instruction — real hardware acceleration, but not a tensor core. This is the same shape of fallback this document already recommends for AMD RDNA1/RDNA2 (see ROCm research above, v_dot2_f32_f16/v_dot4_i32_i8 etc.) — llama.cpp reaches for an ALU dot-product fallback on hardware without tensor cores rather than a naive scalar loop, independently confirming that's the right instinct on both vendors' hardware, not just AMD's.

  • A real, humbling performance data point, directly on point for this

project's actual usage pattern: PR #11583's own measured numbers show the new PTX-mma.sync FlashAttention kernel is 0.87×–0.99× at batch sizes 8–32 (i.e. sometimes slower), with real gains (1.02×–1.50×) only appearing at batch sizes ≥128. boring-llm runs single-user inference (seq≈26, effectively batch=1) — exactly the regime where even the most experienced team working on this exact problem measured a slowdown. See "Composing with existing kernels" below for how this sharpens the benchmark discipline already recommended there.

Metal — simdgroup_matrix<T, Cols, Rows> (MSL 2.3+)

Source: Metal Shading Language Specification (v4.1); Apple Tech Talk "Discover Metal enhancements for A14 Bionic"; WWDC 2026 session 330 ("Optimize custom machine learning operations with Metal tensors").

  • Type: simdgroup_half8x8 / simdgroup_float8x8 only — 8×8 is the

only legal shape, T ∈ {half, float} only (no bf16, no int8, no tf32 in this API). One unconfirmed secondary-source claim of a simdgroup_float4x4 could not be corroborated against the spec text and is likely confusion with the unrelated plain-SIMD simd_float4x4 vertex-math type — treat 8×8-only as the reliable fact.

  • Operations: simdgroup_load, simdgroup_store, simdgroup_multiply,

simdgroup_multiply_accumulate — all four introduced together in MSL 2.3. No separate init function; construction is via the type's own scalar-fill constructor (simdgroup_float8x8 acc(0.0f)).

  • Hardware gate: requires MTLGPUFamily.apple7 (A14/M1 and everything

since — every Mac this backend already targets that isn't an Intel Mac or pre-A14 device). No software emulation path pre-Apple7 — hard unavailable, same as CUDA pre-Volta.

  • Warp/simdgroup-cooperative, same shape as CUDA: "all operations must be

executed only under uniform control-flow within the SIMD-group or the behavior is undefined." Composes normally with simdgroup_barrier around a threadgroup-memory staging step; orthogonal to (not built from) simd_shuffle_*.

  • Not dedicated tensor-core silicon on M1–M4. Direct quote (metal-benchmarks

project): Apple's simdgroup_matrix "decreases register pressure and improves ALU utilization in existing FP32 pipelines" — it runs on the same general FMA/ALU datapath as scalar code, not a separate functional unit. Independent measurement (an M4 Max reverse-engineering writeup) found fp16 matmul2d throughput peaking at ~46% of the scalar-ALU roofline — never above it — and fp8 running slower than fp16 despite half the data, confirming software emulation, not hardware fp8 support. Apple's own A14 numbers frame the win as ~37% average / 22–36% on real conv/Inception workloads — a scheduling/occupancy-efficiency gain, not a CUDA-tensor-core-class 4–16× throughput multiplier. - M5 changes this: a newer, separate "Neural Accelerator" (one per GPU core, genuinely decoupled matrix-multiply hardware) is reachable only through Apple's newer #include <metal_tensor> / matmul2d / "TensorOps" API introduced at WWDC 2026 — not through classic simdgroup_matrix, which still just runs on the ALU path even on M5. This is a materially different, newer API surface and is explicitly out of scope for this proposal (see "Known gaps" and "Sequencing").

  • Composing with Boring's existing 16×16 tile convention: a real tiled

Metal GEMM holds a small 2D array of simdgroup_float8x8 accumulators per simdgroup (e.g. acc[2][2] for a 16×16 logical tile = four 8×8 sub-tile accumulators), looping simdgroup_multiply_accumulate over the sub-tile grid each K-step, then storing all sub-tiles once. This is the natural mapping for LinearKernel's existing 16×16 'actor tiles (see "Composing with existing kernels" below).

ROCm/HIP — MFMA (CDNA only) vs. RDNA's WMMA — the RX 6600 has neither

Source: AMD GPUOpen "Matrix Cores" lab notes; ROCm/amd_matrix_instruction_calculator README; ROCm/rocWMMA README; GPUOpen's RDNA3-WMMA and RDNA4-matrix-core articles; LLVM's GFX10 ISA reference.

  • MFMA (__builtin_amdgcn_mfma_*, ISA v_mfma_*) is exclusive to CDNA

(MI100/MI200/MI300-class datacenter cards, gfx908/gfx90a/gfx940-942/gfx950). AMD's own amd_matrix_instruction_calculator README states it plainly: MFMA is "the ISA-level interface to the Matrix Cores within the AMD Instinct MI100, MI200, and MI300 series processors," while a distinct family, WMMA/SWMMAC, is "the ISA-level interface to the AI Accelerators within the AMD Radeon RDNA 3 and RDNA 4 processors." RDNA1 and RDNA2 appear in neither list.

  • This is the confident, load-bearing finding for this project: the

user's real test hardware, an AMD Radeon RX 6600 (gfx1032, RDNA2), has no dedicated matrix/tensor-acceleration hardware of any kind. GPUOpen's own RDNA2-vs-RDNA3 comparison table lists BF16 throughput as flatly "N/A" for RDNA2 hardware; the FP16/INT8 numbers RDNA2 does report come from ordinary wave32 vector-ALU dot-product instructions (v_dot2_f32_f16, v_dot4_i32_i8, v_dot2_i32_i16, v_dot8_i32_i4 — real ISA instructions, confirmed present since RDNA1/RDNA2 per LLVM's GFX10 reference), not a separate MMA unit. rocWMMA's own supported-architecture list (its GitHub README) confirms this by omission: it lists gfx9xx (CDNA) and gfx11xx/gfx12xx (RDNA3/RDNA4) — gfx1030/gfx1032/gfx1031/etc. (RDNA2) and any RDNA1 target are simply absent, because there is no hardware underneath for the library to lower onto. Sources agree on this with no ambiguity.

  • rocWMMA's C++ API is a deliberate 1:1 mirror of CUDA's nvcuda::wmma —

rocwmma::fragment, load_matrix_sync, mma_sync, store_matrix_sync — per ROCm's own docs, easing a shared Boring-side abstraction.

  • MFMA is directly callable from ordinary HIP device code (no inline

asm required for basic use) — confirmed via AMD's own worked example calling __builtin_amdgcn_mfma_f32_16x16x4f32(...) inline in a __global__ kernel. It requires compiling with a CDNA --offload-arch (e.g. gfx90a); no RDNA --offload-arch exposes __builtin_amdgcn_mfma_* at all — RDNA3+ instead exposes the distinct __builtin_amdgcn_wmma_* family.

  • Fixed CDNA2 tile shapes (from AMD's own table): FP32 accumulate —

32×32×2, 32×32×1, 16×16×4, 16×16×1, 4×4×1; FP16/INT8/BF16 input — 32×32×8, 32×32×4, 16×16×16, 16×16×4, 4×4×4; FP64 — 16×16×4, 4×4×4. Exact shape sets shift generation to generation (CDNA1/2/3 each add/change combinations).

  • Boring-specific complication: boring build --target rocm (the

transpiler) does not know the real target GPU architecture — that's chosen later, at cargo build time, via BORING_ROCM_ARCH consumed by build.rs's hipcc --genco invocation (see rocm-backend.md). This means the transpiler cannot simply "check the arch and pick MFMA or fallback" the way it might for CUDA/Metal — the arch isn't known until a build step the transpiler doesn't control. See "Per-backend lowering" below for the proposed fix (emit both code paths, let the C preprocessor pick).

wgpu/WGSL — a real gap today, but actively closing upstream, not permanent

Source: W3C WGSL/WebGPU spec (Candidate Recommendation Draft); gpuweb issues

#4195 ("Subgroup matrix"), #4137, #3950; gpuweb/gpuweb's proposals/subgroup-matrix.md explainer; gfx-rs/wgpu PRs #8251, #9490,

#10414; wgpu-types Features docs.

  • No cooperative-matrix/tensor primitive exists in the ratified WGSL spec

today, and none exists in the wgpu version this project pins (~v22, mid-2024).

  • This is not a dead or purely-hypothetical gap, though. gpuweb has an

active "subgroup-matrix" proposal (subgroup_matrix_left<T,K,M>/ _right<T,N,K>/_result<T,N,M> WGSL types; component types f32/f16/ u32/i32/u8/i8; Vulkan/Metal backend mappings drafted, a D3D12 mapping added as recently as 2026-09-22) — status "Draft," not yet spec-merged, with live design churn as of meeting notes from 2026-01 and 2026-03.

  • wgpu/naga already has real, merged, non-standard support ahead of the

standard settling: Features::EXPERIMENTAL_COOPERATIVE_MATRIX (merged 2025-12-22, PR #8251) adds a coop_mat WGSL type plus coopLoad/ coopStore/coopMatMulAdd, targeting Vulkan (VK_KHR_cooperative_matrix) and Metal (simdgroup_matrix under the hood) — initially limited to 8×8 f32 only, with follow-on work (non-square tiles, PR #10414 open as of 2026-09-21; integer types, PR #9490 closed as a draft needing rework) still landing. None of this reaches the DX12 backend yet. None of it is in any shipped browser (Chrome/Dawn carries only an internal experimental flag). Crucially, all of this postdates wgpu v22 by 1.5+ years and 6+ major versions — nothing here is usable at Boring's current wgpu pin.

  • Honest framing for this design: the wgpu backend needs a real

software-fallback story today and for the near-to-mid term — but the right posture is "track Features::EXPERIMENTAL_COOPERATIVE_MATRIX as the likely native path once Boring's wgpu pin is bumped past ~v28," not "assume permanent absence." This mirrors the exact wording already used for other wgpu gaps in wgpu-backend.md's "Will these gaps close?" section — some gaps there are "Boring-side integration gaps" (closable unilaterally), others are "genuine spec-level gaps" (outside wgpu's control, slow). This one is closer to the first bucket once the pin moves, and to the second bucket (an actual upstream spec dependency) until then.

Proposed design

Why a namespace + new builtin types, not a qualifier

gpu.warp.* is a namespace of built-in values and functions — it needed no new type, because a warp shuffle just moves an existing scalar between registers of the same shape it already had. A tensor-core fragment is different in kind, not degree: it is an opaque, hardware-defined, multi-lane-cooperative aggregate whose logical shape (M, N, K) and role (A/B/accumulator) is part of its type — exactly why every vendor models it as a distinct type rather than a qualifier on an existing scalar/array (wmma::fragment<Use, M, N, K, T, Layout>, simdgroup_matrix<T, Cols, Rows>, rocwmma::fragment<...>). Boring's existing qualifiers ('actor, 'global, 'unified, …) all describe the memory/ownership semantics of a binding whose element type is otherwise ordinary — they compose with [T]/[T, N], they don't replace the type. Inventing a 'frag qualifier would force an awkward question ("qualifier on what base type?") that every vendor's own API answers by making the fragment a type of its own. So: new builtin generic types under a gpu.tensor namespace, with methods on them — following the vendor precedent more faithfully than a qualifier would, while still nesting under the existing gpu built-in the same way gpu.warp does.

Types

boring
gpu.tensor.MatrixA<int M, int K, dtype T, Layout = gpu.tensor.RowMajor>
gpu.tensor.MatrixB<int K, int N, dtype T, Layout = gpu.tensor.RowMajor>
gpu.tensor.Accumulator<int M, int N, dtype T>

Layout is one of two builtin tag types, gpu.tensor.RowMajor / gpu.tensor.ColMajor — mirroring wmma::row_major/col_major and rocwmma's identical convention. An Accumulator fragment carries no Layout type parameter (matching CUDA/HIP: accumulator layout is passed to the load/store call itself, not baked into the type — the accumulator is logically layout-agnostic in-register, it only has a layout once written to memory).

M, N, K, T (and the CUDA-only precision::tf32-style narrowed dtypes) are checked against the current --target's own legal shape/type table at compile time — an illegal combination (e.g. gpu.tensor.MatrixA<16, 16, float32> on --target metal, where only 8×8 half/float32 is legal) is a hard compile error naming the offending backend and its actual legal set, the same style CUDA/Metal/ROCm/wgpu already use elsewhere in this project for target-specific hard errors (e.g. wgpu's float64 rejection).

Methods

All only callable inside a kernel def() body (device-side), like gpu.warp.*, and inherit the identical divergent-branch caveat: every lane in the warp/simdgroup/wavefront must execute the same call at the same program point, or behavior is undefined — Boring doesn't detect or warn about this today, matching gpu.warp.*'s own documented, unsolved caveat.

gpu.tensor.available — the compile-time capability query

A single builtin bool constant, resolved per --target (and, for CUDA, per the same architecture-targeting knob proposed as prerequisite work below):

boring
if gpu.tensor.available:
    # use gpu.tensor.* fragments
else:
    # existing plain tiled shared-memory loop

This is deliberately an ordinary Boring if, not new conditional-compilation syntax — kernel authors already know how to write one. Per-backend behavior:

  • CUDA: true once a minimum-SM knob (proposed prerequisite, see

"Sequencing") is set to sm_70+; false (with a checker warning, not a hard error, if gpu.tensor.* is used inside the true branch anyway) otherwise.

  • Metal: resolved at runtime, not transpile time — Metal already

compiles MSL at app-startup via newLibraryWithSource (see metal-backend.md), so, exactly like wgpu's existing Features::SUBGROUP dual-shader-module pattern, the Metal backend emits two .metal variants (one using simdgroup_matrix, one the existing plain tiled loop) and picks between them via device.supportsFamily(.apple7) before first dispatch. This reuses a pattern this project has already shipped once.

  • ROCm: resolved at HIP-compile time via C preprocessor branching on

a target-architecture macro that hipcc/clang predefines for whatever --offload-arch BORING_ROCM_ARCH resolves to (the exact macro form needs verification against a real hipcc invocation before implementation — this is called out as a Phase 3 prerequisite, not asserted as already-verified fact). The transpiler emits both branches unconditionally into the generated .hip source (mirroring wgpu's dual-module strategy, but via #if/#else instead of a runtime feature query, because ROCm's target architecture is a compile-time fact the transpiler itself doesn't have early enough to choose between two Rust-level source files the way Metal/ wgpu can). RDNA1/RDNA2 (including gfx1032, the RX 6600) always take the #else (fallback) branch — there is no hardware to gate #if toward.

  • wgpu: false, unconditionally, at the pinned wgpu version — no

runtime query needed since the feature doesn't exist there at all yet (see vendor research above). Revisit once the wgpu pin moves past the version that ships Features::EXPERIMENTAL_COOPERATIVE_MATRIX.

  • boring run (interpreter): true, unconditionally — gpu.tensor.* is

fully simulable on the CPU as a plain dense matrix multiply over the fragment's declared shape (no real hardware behavior to emulate, unlike gpu.warp.*'s per-warp barrier/shuffle simulation — a tensor-core MMA has no cross-lane synchronization semantics visible to a correctness-only simulation, only a throughput characteristic that's meaningless on the CPU). Lets kernel authors validate correctness with no GPU at all, same workflow as every other kernel primitive today.

Important limitation, stated plainly: gpu.tensor.available answers "does this hardware have any tensor acceleration," not "is this specific (M,N,K,T) combination legal here." A fragment declaration with an illegal shape for the current target is still a hard compile error inside the true branch — gpu.tensor.available does not paper over the fact that CUDA's smallest wmma tile family (16×16×16 fp16/int8/bf16, or 16×16×8 tf32) and Metal's only legal shape (8×8×8, half/float only) share no common tuple at all. A kernel wanting a tensor-core path on both CUDA and Metal needs two distinct fragment declarations (and, in practice, two distinct kernel structs or a --target-selected variant) — this document does not propose an auto-decomposing "one declaration, N backends" abstraction (see "Known gaps," item 1, for why that's explicitly out of scope for now).

CUDA — recommended shape/type coverage for Phase 1

  • fp16 in → fp32 accumulate, 16×16×16 (and 32×8×16/8×32×16 for

non-square tiles) — the standard, best-supported combination, sm_70+.

  • int8 in → int32 accumulate, same shapes, sm_75+ — this is the

highest-value target for this project specifically: Q8LinearKernel already stores Q8_0 weights as raw signed int8 values with a per-block fp16 scale (see boring-llm/src/math_gpu.br). A tensor-core path here could load the raw quantized int8 bytes directly into a MatrixB fragment (skipping the current per-thread dequantize-to-float32 step entirely inside the hot loop) and apply the block scale once, after mma_sync, to the int32 accumulator. This isn't a hypothetical optimization — it's structurally the same kernel llama.cpp's own MMQ path already is (see "What llama.cpp actually does" above): fused dequant + int8 tensor-core dot product, int32 accumulate. Real, independently-arrived-at precedent for exactly this design, not just a theoretical fit.

  • tf32 (16×16×8 only, sm_80+, needs the source to call

__float_to_tf32 before .load() — modeled as a frag.load_tf32(src, ld) variant, or an implicit conversion the checker inserts when T is declared gpu.tensor.TF32): a reasonable stretch item, not required for Phase 1.

  • wmma.h C++ is proposed as the Phase 1 starting point, not the

end state. It's the simplest, most conservative surface to validate the new parser/checker machinery against (matches this project's existing "verify via codegen-snapshot tests first" style for untestable-locally CUDA features). But llama.cpp's own migration away from wmma:: for anything newer than Volta (above) is real signal that a Phase 1.5 revisiting the hot kernels (Q8LinearTensorCoreKernel in particular) with raw PTX mma.sync — once the wmma.h-based primitive is shipped and validated — is a reasonable, evidence-backed follow-on, not a speculative one. This is a materially different, lower-level codegen surface (hand-written register-level PTX asm rather than a C++ template call) and should be its own follow-up task, not conflated with Phase 1's simpler goal of proving the primitive works at all.

  • Explicitly out of scope for both the wmma.h-based Phase 1 and the raw

mma.sync Phase 1.5: fp8 (Ada+) and Hopper's wgmma warpgroup-async family need a genuinely different instruction family and target hardware generation this project has no way to test against locally. Flagged as a distinct, later follow-up if the project ever specifically needs Hopper-class hardware, not bundled into this proposal.

Metal — recommended coverage for Phase 2

  • fp16 in → fp32 accumulate, 8×8×8, the only legal shape — full stop.
  • Dual-module runtime dispatch (device.supportsFamily(.apple7)), as

described above — keeps Metal builds running correctly (via the existing plain-tiled fallback) on Intel Macs and pre-A14 Apple Silicon.

  • Expectation-setting, stated plainly in the doc a kernel author would

read: because classic simdgroup_matrix runs on the same ALU pipeline as scalar FMA on every currently-common Mac (M1–M4), the realistic payoff here is Apple's own documented ~30–40%-class occupancy/register-pressure win — not a CUDA-tensor-core-class multiple. The newer M5 Neural Accelerator path (matmul2d/TensorOps) is real dedicated hardware but is a different, newer API, explicitly out of scope for this proposal (see "Known gaps").

ROCm — recommended gating and coverage for Phase 3

  • CDNA targets (gfx908, gfx90a, gfx940–gfx942, gfx950): real

MFMA hardware. Prefer rocWMMA's CUDA-mirroring C++ API (rocwmma::fragment/load_matrix_sync/mma_sync/store_matrix_sync) over hand-emitting raw __builtin_amdgcn_mfma_* calls where possible — it's a vendor-maintained, tested library sitting on top of the same intrinsics, and its API shape requires near-zero change to the CUDA-backend codegen logic already written for wmma.

  • RDNA3/RDNA4 targets (gfx11xx, gfx12xx): real WMMA "AI accelerator"

hardware, a different instruction family from CDNA's MFMA (__builtin_amdgcn_wmma_*) — rocWMMA's own supported-architecture list covers these too, so the same library-first strategy applies, but the underlying codegen path is genuinely distinct from the CDNA one and needs its own validation (this project has no RDNA3/4 hardware to test against today, only the RDNA2 RX 6600 — flagged as an untestable-locally gap, the same honest caveat this project's docs already carry for CUDA).

  • RDNA1/RDNA2 targets (gfx101x, gfx103x — including gfx1032, the

RX 6600): always the fallback branch, unconditionally. No #if probes a real capability here because there's nothing to detect — the finding is unambiguous (see vendor research above). The fallback itself is proposed in two tiers: Phase 3a (safe, simple) reuses the exact plain shared-memory-tiled loop LinearKernel/Q8LinearKernel already use — i.e. gpu.tensor.available == false on this hardware simply means "nothing changes, write the loop you'd write today." Phase 3b (real, but a later stretch) would target RDNA2's actual v_dot2_f32_f16/v_dot4_i32_i8-style ALU dot-product instructions via their own Clang/LLVM builtins — genuine, real hardware acceleration, just not "tensor cores," and a distinct, separate design exercise from this one (closer in spirit to a gpu.warp.*-style addition than to gpu.tensor.*).

wgpu — Phase 4, software fallback only, with an explicit upstream trigger to revisit

  • gpu.tensor.available is false. The else branch — Boring's existing

tiled shared-memory GEMM pattern (var<workgroup> tiles, workgroupBarrier()) — is the permanent, documented codegen for this backend at the current wgpu pin.

  • Concrete revisit trigger, not vague "someday": once Boring's wgpu

dependency is bumped to a version shipping Features::EXPERIMENTAL_COOPERATIVE_MATRIX (merged at wgpu ~28.x, Vulkan+Metal only, 8×8 f32 initially), re-run this feasibility exercise — the runtime-feature-query + dual-shader-module pattern this project already ships for gpu.warp.*'s subgroup fallback applies here verbatim.

Composing with existing kernels — what actually has to restructure

The task here isn't abstract: boring-llm's LinearKernel/Q8LinearKernel (src/math_gpu.br) are real, already-shipping 16×16-tiled GEMM kernels using 256 threads (a 16×16 block) to compute one 16×16 output tile, one scalar accumulator per thread. Adopting gpu.tensor.* is not a drop-in swap of the inner reduction loop — it changes the fundamental thread-to-output mapping:

  • Today: 256 threads, each owning one scalar accumulator (acc), each

independently walking the 16-wide for kk in 0..<16: acc += tile_x[...] * tile_w[...] reduction after a shared-memory tile load sync barrier.

  • With gpu.tensor.* (CUDA, 16×16×16 fp16 fragments): one warp (32

threads) computes the entire 16×16=256-element output tile via a single acc.mma(a, b) call per K-step — the block's thread count doesn't need to drop to 32 (multiple warps can each own a different output tile within the same block, keeping occupancy up), but the loop structure changes from "256 threads, 1 output element each" to "N warps, 1 whole 16×16 tile each." Shared-memory tile loading also changes shape: cooperative fragment loads read directly from the 'actor tile (32 threads loading a 16×16=256-element tile means each thread loads/stages 8 elements instead of today's 1:1 mapping), and Q8LinearKernel's inline dequantization must move earlier — either dequantize into the shared-memory tile before the fragment load (since .load() reads raw memory of the fragment's own element type, not an arbitrary expression), or — the higher-value option specifically because the weights are already int8 — skip dequantization inside the hot loop entirely and load the raw quantized bytes straight into an int8 MatrixB fragment, applying the per-block fp16 scale once to the int32 accumulator after mma_sync (see "CUDA — recommended shape/type coverage" above).

  • With gpu.tensor.* (Metal, 8×8×8 fp16/fp32): the existing 16×16 tile

maps cleanly onto a 2×2 grid of simdgroup_float8x8 accumulators per simdgroup — a smaller restructuring than CUDA's, since the tile size Boring already picked (16×16) happens to be an exact small multiple of Metal's fixed 8×8 unit.

This must be benchmarked, not assumed to win — exactly the lesson LinearWarpKernel's own doc comment in math_gpu.br already learned the hard way (a gpu.warp.*-based rewrite that removed barriers but lost shared- memory data reuse came out slower, not faster, on real hardware). Reducing per-tile thread count from 256 to 32 (one warp) trades scalar ALU parallelism for tensor-core throughput-per-instruction — whether that nets a win depends on real GPU occupancy characteristics for this project's actual shapes (d_in/d_out/seq at Qwen2.5-0.5B's scale), not on FLOP-counting alone.

This isn't just an internal, single-data-point caution — llama.cpp's own real measurements say the same thing, more starkly. PR #11583 (see "What llama.cpp actually does" above) reports its PTX-mma.sync FlashAttention kernel at 0.87×–0.99× (slower) at batch sizes 8–32, with real wins (1.02×–1.50×) only past batch ≥128. boring-llm is single-user inference — seq≈26, effectively batch=1 — squarely inside the regime where the most experienced team working on this exact class of kernel measured a regression, not a win. This doesn't mean a tensor-core rewrite is pointless for boring-llm — GEMM (this project's LinearKernel/Q8LinearKernel) and FlashAttention have different arithmetic intensity profiles, and MMQ-style kernels (structurally closer to Q8LinearKernel) aren't the same kernel PR #11583 measured — but it is a concrete reason to treat "small-batch tensor cores may not help, and might hurt" as the null hypothesis to disprove, not background noise to note in passing.

Any Phase 1 CUDA kernel built from this proposal should ship as a new, independently-verified variant alongside linear_gpu/q8_linear_gpu — the same pattern linear_warp_gpu already established — and only replace the existing kernels if it's measured to actually win at this project's real sizes.

Known gaps and limitations

  1. No cross-backend tile-shape portability. CUDA's smallest wmma

family (16×16×16, or 16×16×8 for tf32) and Metal's only legal shape (8×8×8) share zero common (M, N, K) tuples. gpu.tensor.* unifies the operation surface, not the tile geometry — a kernel targeting tensor-core acceleration on both CUDA and Metal needs two distinct fragment declarations today. An auto-decomposing higher-level type (e.g. a gpu.tensor.Tile<M,N,K,T> that transparently tiles itself into however many hardware-native sub-fragments a given backend needs) is a real, plausible future design — deliberately not proposed here, because it's a materially larger and riskier transpiler undertaking (generated nested loops managing multiple backing fragment variables) that this document's own instructions call out as exactly the kind of complexity not to take on in one sitting without first validating the simpler primitive-level design. 2. Divergent-branch safety is inherited, unsolved, same as gpu.warp.*. Every gpu.tensor.* method call needs uniform control flow across the warp/simdgroup/wavefront; Boring doesn't detect or warn about a call inside non-uniform control flow today. 3. CUDA needs a new architecture-targeting knob it doesn't have today. Unlike ROCm's BORING_ROCM_ARCH, docs/cuda-module.md shows no existing mechanism for choosing a minimum compute capability / -gencode flag for nvcc. gpu.tensor.* needs sm_70+ at minimum — this is a real prerequisite gap, not just a nice-to-have, since without it there's no principled way to set gpu.tensor.available for CUDA at all. Proposed as Phase 0 prerequisite work. 4. ROCm's RDNA1/RDNA2 exclusion is permanent, not a "not yet." Confirmed directly against AMD's own hardware/library support lists — there is no future ROCm release that will make MFMA or WMMA exist on gfx1032 silicon. The fallback path is the only sound target for this project's real RDNA2 test hardware, indefinitely. 5. wgpu's gap is real today but explicitly not structural — see vendor research above. Re-evaluate once Boring's wgpu pin moves past the version shipping Features::EXPERIMENTAL_COOPERATIVE_MATRIX. 6. fp8 and Hopper's wgmma family are out of scope — a distinct, later follow-up if the project ever needs Hopper-class hardware specifically. Raw PTX mma.sync itself (as opposed to wgmma/fp8) is not in this bucket, though — llama.cpp's own migration away from wmma:: C++ (see "What llama.cpp actually does") is real evidence it's a worthwhile Phase 1.5 follow-on, just a distinct, riskier codegen surface from Phase 1's wmma.h-based starting point, not bundled into it. 7. Metal's classic simdgroup_matrix is not dedicated hardware on M1–M4 — set expectations accordingly (a ~30–40%-class occupancy win, not a multiple). The M5 Neural Accelerator's real dedicated hardware is reachable only through a newer, different API (matmul2d/TensorOps, WWDC 2026) — explicitly a separate design exercise, not folded into this proposal, to avoid conflating two materially different Metal features under one name. 8. No kernel in this project has been rewritten or benchmarked yet. Every performance claim above is vendor-documented theoretical throughput, not a measurement against boring-llm's real shapes — see "Composing with existing kernels" for why this specifically must be verified, not assumed.

Feasibility and sequencing

Each phase below is sized to become its own discrete follow-up task, the same granularity this project already tracks GPU-kernel bug fixes at.

  • Phase 0 — prerequisites (blocks every other phase):

- Add an explicit CUDA architecture-targeting knob (mirroring BORING_ROCM_ARCH) so gpu.tensor.available has something principled to gate on. - Parser/checker support for gpu.tensor.MatrixA/MatrixB/Accumulator<...> as local-variable types inside a kernel def() body — new surface area (today's const generics, e.g. Blur<int N>, only appear on struct/kernel declarations, never as an ad hoc local variable's own type) and the riskiest new parser work this proposal implies. Validate this in isolation before attempting any backend codegen. - gpu.tensor.available as a builtin compile-time/runtime bool, per the per-backend resolution rules above.

  • Phase 1 — CUDA (wmma.h), highest value, most standardized backend.

fp16→fp32 and int8→int32, 16×16×16-family shapes. Ship a new LinearTensorCoreKernel/Q8LinearTensorCoreKernel alongside (not replacing) linear_gpu/q8_linear_gpu, and benchmark at this project's actual batch=1/seq≈26 scale before considering a swap — llama.cpp's own PR #11583 numbers (slower at batch 8–32, wins only past batch≥128; see "What llama.cpp actually does") make this the default expectation to disprove, not a formality. Unverified against real NVIDIA hardware in this dev environment, same standing caveat every other CUDA feature in this project already carries.

  • Phase 1.5 — CUDA, raw PTX mma.sync (follow-on to Phase 1, only after

it's validated): revisit Q8LinearTensorCoreKernel with hand-generated PTX instead of wmma.h, following llama.cpp's own precedent of moving off wmma:: C++ for exactly this reason (fixed fragment layout capping performance). A materially riskier codegen surface (register-level PTX asm generation, not a C++ template call) — scoped as its own task, not bundled into Phase 1.

  • Phase 2 — Metal (simdgroup_matrix). 8×8 fp16/fp32 only, dual-module

runtime dispatch on MTLGPUFamily.apple7. Real hardware to verify against (this project's Metal backend is actively verified locally). Expect a modest win, not a multiple — set that expectation up front in the PR/task description so a "only 1.3×" result isn't read as a failure.

  • Phase 3 — ROCm. 3a: preprocessor-gated dual-path codegen, CDNA→rocWMMA,

RDNA3/4→rocWMMA (its RDNA coverage), RDNA1/RDNA2→existing fallback unconditionally. Verify the real HIP/clang arch-macro mechanism against a real hipcc invocation before implementing the #if gating (flagged above as unverified). Real, hardware-verifiable fallback-path testing on the project's existing RX 6600 (confirms the #else branch is taken and produces identical output to today's plain kernel — no MFMA/WMMA path testable locally without CDNA/RDNA3+ hardware, matching this project's existing "verified as far as hardware allows" caveats elsewhere). 3b (stretch, separate task): RDNA2 v_dot* ALU-instruction acceleration — real hardware acceleration, not tensor cores, a distinct design exercise.

  • Phase 4 — wgpu. Software-fallback-only, gpu.tensor.available = false

permanently at the current pin. No implementation work beyond making sure the else branch of any gpu.tensor.*-using kernel compiles correctly on this backend. Revisit as its own future task once the wgpu dependency is bumped past the version shipping Features::EXPERIMENTAL_COOPERATIVE_MATRIX.

The parser/type-system change in Phase 0 (a new kind of generic local-variable type) is real, non-trivial surface area that this research pass did not attempt to validate against the real parser — attempting a "minimal" CUDA-only prototype without first landing and validating that prerequisite would risk shipping a syntax shape that doesn't actually fit Boring's grammar, which is worse than proposing a well-reasoned design and sequencing it properly.
