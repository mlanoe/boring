2. Feasibility analysis — challenges per component

2.1 Value (enum with 25+ variants)

rust
pub enum Value {
    Nil, Void, Bool(bool), Int(i64), Uint(u64), Float(f64),
    Str(String), Array(Vec<Value>), Tuple(Vec<Value>),
    Dict(Vec<(Value, Value)>), Set(Vec<Value>),
    Object(Rc<RefCell<ObjectInner>>),
    EnumVariant { type_name, variant, fields },
    Fn { decl: FnDecl, captured: EnvRef },
    Closure { params, body, captured },
    NativeFn { name, func: fn(&[Value], usize) -> Result<Value, Signal> },
    OverloadedFn { name, variants },
    Channel { buf: Rc<RefCell<VecDeque<Value>>>, ... },
    ...
}

Challenges:

  • NativeFn holds a Rust function pointer. In Boring, a function type Value([Value]) in a field position is transpiled to Rc<dyn Fn(Vec<Value>) -> Value> — storable and cloneable. The NativeFn variant was ported directly without structural changes.
  • The Fn and Closure variants hold captured: EnvRef which is Rc<RefCell<Env>>. In single-threaded Boring, Rc<RefCell<T>> is generated by the transpiler via T'actor — no issue.
  • Channel with a shared Rc<RefCell<VecDeque<Value>>> between sender and receiver — same remark.

2.2 Env (chained scopes)

rust
pub struct Env {
    vars: HashMap<String, Value>,
    mutable: HashSet<String>,
    shared_mutable: HashSet<String>,
    parent: Option<EnvRef>,     // EnvRef = Rc<RefCell<Env>>
}
pub type EnvRef = Rc<RefCell<Env>>;

Env is a tree of scopes shared via Rc<RefCell>. Closures capture their parent EnvRef. This is the heart of the execution model.

In Boring: the structure ports directly. HashMap is available in the stdlib. The recursive Env → parent: Option<EnvRef> is expressed as parent: Env'actor?, which transpiles to Option<Rc<RefCell<Env>>> — pointer-sized, no indirection issue.

2.3 Mutual recursion between exec / eval_expr / call

All three modules call each other through self (the Interpreter struct). Ported into a single Interpreter'actor struct in Boring, passed as a parameter. Call dispatch was integrated into eval.br rather than kept as a separate module.

2.4 Native stdlib (~540 lines in stdlib.br)

Approximately 30 native functions (print, write, len, int, float, string, math functions, etc.) are registered via NativeKind enum dispatch. Native functions are stored as Rc<dyn Fn(Vec<Value>) -> Value> (from function-literal fields in Boring).

2.5 Built-in methods (methods.br, 1 000 lines)

All methods on Array, Dict, Set, String, Range, Channel, etc. — dispatched via call_method. Ported 1-to-1 as a straightforward data-manipulation port.

4. Architecture — what was built

The Boring interpreter is a self-contained pipeline:

source.br → Boring lexer → Boring parser → Boring interpreter → output

No JSON serialization round-trip was needed. The entry point (main.br) calls the Boring lexer and parser directly, then runs the Boring interpreter. The Rust front-end is bypassed entirely.

Both emission modes are supported:

  • boring/interpreter/main_rust — multi-thread (Arc<Mutex<T>> for 'actor) via boring build --threading multi
  • boring/interpreter/main_rust_single — single-thread (Rc<RefCell<T>> for 'actor) via boring build --threading single

8. Remaining gaps

8.1 VecDeque<T> (low impact)

Value::Channel uses Rc<RefCell<VecDeque<Value>>> for the internal buffer. VecDeque provides O(1) push-back / pop-front semantics, while Vec has O(n) pop-front.

Current Boring support: Vec-backed arrays only. No VecDeque.

Workaround in use: regular [Value] array with remove(0) for pop-front. Performance is O(n) but acceptable for the interpreter's simulation-only channels.
